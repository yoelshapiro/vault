Parking Capability — Architecture Research

The release driving model is a stateless, fixed-window policy: 1 s of video in, 2 s of trajectory out, no memory across ticks. The task: extend it to the full parking ladder — street parking through multi-story lots, gates, preferred spots, and memory parking (R1–R6). Basic parking is reachable with curated data; the harder tiers expose three structural gaps — a too-short horizon (G1), unhandled multimodality (G2: which spot, which maneuver, when to commit), and no memory (G3: searched area, lot rules, stored spots). This report is the full, adversarially-reviewed proposal: six solution families that compose into one architecture, kept production-viable under the frozen-trunk multi-head deployment paradigm.

01

TL;DR — seven pieces, one architecture

The network stays a stateless parking head on the frozen shared trunk. Everything that must persist lives in an external Parking Memory Service and re-enters as tokens. A slow ~1 Hz strategic loop chooses where to park and via which legs; the fast tick loop only executes the committed leg. Click a card to jump to the full design.

P0 · PREREQUISITES
Representation decisions first
The three recorded street-PUDO failures are representation symptoms, not bugs: add HOLD/dwell semantics, fix termination contracts, run a one-week reverse diagnostic, unify everything on one gear-aware LegCode vocabulary.
S1 · PRX HEAD
Propose → Rank → eXecute
One stateless head that makes the spot/maneuver choice explicit, rankable and conditionable — anchored-truncated diffusion restores on-car multimodality in ~2 denoise steps.
S2 · LEG CODEBOOK
Long horizon as structure, not length
A maneuver becomes an AR sequence of gear-delimited legs (POLICY_PARKING_LEGS); autoregression at the leg level only, single-shot within a leg, 2 s controller contract untouched.
S3 · MEMORY AS INPUTS
Parking Memory Service
Coverage, spot inventory, rules, stored spots and the committed plan live outside the network and re-enter the parking head as tokens — inspectable, replayable, retrain-proof.
S4 · DATA ENGINE
Fleet logs → parking supervision
HER/GCSL goal relabeling, GPS-resolution lot priors, first-vs-second-lap contrast pairs, and a VLM attribute pipeline — scoped to what survived the data-realism critique.
S5 · DECISION LAYER
Critic-as-ranker + commitment
The existing C51 critic re-deployed as a shadow-first plan ranker (V-GPS pattern), plus hysteresis so a stateless network stops changing its mind every tick — with an explicit abort/recovery state machine.
S6 · RIDERS & GYMS
Other teams' trains, made visible
WFM latent-action pretraining is off the 2026 critical path; 3DGS lot gyms are promoted (the only credible source of search-behavior signal); gates are behavior + ops, not architecture.
HONESTY CLAUSE
Mostly disciplined integration
By design: the brief is production, not publication. The defensible novel bits are (a) the gear-aware leg-code vocabulary under the frozen-trunk constraint and (b) memory-as-input wiring with an explicit commitment layer.

The model today

Grounded in code, 2026-06-12. Entry point wayve/ai/si/configs/baseline/release.py — one config for BC + RL; WFM pretrain lives in wayve/ai/foundation/models/world_model. Hover any block for details and file references.

Release model (BC + RL share this I/O). Hover blocks for code references. Only caches: sliding-window ViT/radar feature caches (pure compute saving) + a deployment-wrapper indicator memory outside the network.

Statelessness, confirmed

No recurrent state crosses inference ticks. Fixed-window policy: 1 s in / 2 s out. The “memory” precedent people cite — indicator memory — is a deployment-wrapper buffer outside the network (deployment_wrapper.py:826).

Multimodality device

The only one: the 961-way latent-action endpoint grid — a radial-exponent grid tuned for forward driving. Dense near origin, sparse at range, no reverse semantics. And it's disabled in every production parking config.

Why this matters for parking

Parking needs multi-leg gear-reversing plans beyond 2 s, an explicit representation of discrete choices, and task state over minutes. No current component carries any of the three.

03

The problem — six requirements, three gaps

The requirements ladder is incrementally complex. Click a requirement to see which structural gaps it stresses and which solutions cover it (cross-highlighted in the coverage matrix). A fourth, implicit gap — G4 sensing/data (rear/fisheye cameras, USS, spot labels) — is tracked by the 2026 roadmap; it constrains this research but is not its focus.

The three gaps

G1 — Longer horizon

The 2 s trajectory is too short for multi-leg maneuvers and search behavior. The 24.5 m distance-parameterized POLICY_PATH helps at parking speeds, but cannot represent gear reversals or waits.

G2 — Multimodality

Choice of spot, type of maneuver, where to start the maneuver. The only existing device (961-way endpoint grid) is geometry-tuned for forward driving — and off in parking configs.

G3 — Memory / ICL

Efficient search (don't revisit), persistent sign/rule constraints (“level 2 reserved”, height limits), stored personal spots (R6). Scope decision: external memory only — the network stays stateless; internal recurrence is out of scope.

Synthesis (§5 of the research doc)

The release model is a stateless, fixed-window (1 s in / 2 s out) feed-forward policy whose only multimodality device is geometry-tuned for forward driving. Parking needs: (a) plans that span multi-leg, gear-reversing maneuvers well beyond 2 s; (b) an explicit, conditionable representation of discrete choices — which spot, which maneuver class, when to commit; and (c) persistent task state over minutes that no current component can carry. The four existing approaches each cover a slice: A1 (choice, wrong geometry), A2 (horizon + implicit multimodality, single proposal on car), A3 (choice + horizon, wrong stack), A4 (the unifying idea, unbuilt). None addresses G3 at all.

History note: the Jan-12 pivot bet “no architecture change needed — data balancing suffices” was made for PUDO only; this research is explicitly about where that bet stops holding. Recorded guidance to avoid in-context-learning research (May-5 weekly) is in direct tension with G3 — resolved by the scope decision: memory enters only as inputs, maintained outside the model.

04

Existing approaches — actual status in code

Four lines of prior work were traced through the repo, sibling branches, Notion logs, and four Google-Drive design docs. Badges reflect what actually exists, not what READMEs claim.

A1 · Latent actions in release OFF for parking

Implemented and on in the release baseline, but the parking output adaptor sets enable_latent_action=False (parking_config.py:534-535) — the parking README claim that it uses latent actions is stale. Notion experiment logs show the LA grid is a log-polar/radial-exponent grid tuned for forward driving: dense near origin, sparse at range, no reverse semantics — exactly weakest where parking lives (low speed, reverse, multi-leg).

A parking-capable LA space likely needs a different parametrization — gear-aware, maneuver-aware. That becomes P0's LegCode.

A2 · Diffusion path head merged · most mature

wayve/ai/zoo/outputs/diffusion.py (1,492 lines) + parking_diffusion_datamodule (parking_config.py:291-514). Diffuses POLICY_PATH: 50 poses @ 0.5 m = 24.5 m of distance-parameterized geometry (not time!) — a long effective horizon at parking speeds; yaw π-flip encodes reverse legs. DDIM v-prediction, 2 MMDiT blocks (d=768), 5–10 denoise steps on car. Two-stage: diffusion plans the path → PolicyPathConditioner → cheap OrdinaryHead decodes the executable 11-frame trajectory + gear + indicator.

Multimodality exists at training/eval only: 10–50 noise samples, best-of-K metrics; on-car uses zero initial noise → deterministic single proposal (diffusion.py:1457). POLICY_PARKING_POSE confidence is a placeholder 1.0 — “revisit when ranking multiple proposals” (diffusion.py:415). No spot conditioning on main: the PARKING_POSE goal is computed in the datamodule (with CFG-style dropout plumbing) but no input adaptor consumes it. The parking_bc_diffusion mode itself was removed by c1069f4c73a8; datamodule + zoo head remain.

A3 · “Multi-head WTA” (zmurez/pudo) branch-only · experimental stack

607 commits, all in the experimental MCV Perceiver stack (wayve/ai/experimental/), not the SI baseline. Not actually min-over-heads: MultiStepARConv does autoregressive discrete goal classification over a 640×640 BEV grid at horizons 8 s / 4 s / 2 s, plus a first step predicting the final parking spot. Hindsight CE targets, teacher forcing with a self-forcing schedule. At inference each step is argmax (= the “WTA”); the winning cell's SinCos embedding is injected back as a token — the goal embeddings are latent actions conditioning a single regression head (40 waypoints @ 0.2 s = 8 s horizon).

Plus: “winner-takes-control” deployment interleave, park-type/stop-reason/intention/quality heads from ~230k annotations, hazard-park/PUDO samplers, OSM synthetic PUDO route generator. The real WTA loss on this branch is in the addenda below.

A4 · AR spots → LA → trajectory idea only

The full chain (predict candidate spots → condition LA on chosen spot → AR-decode trajectory) is implemented nowhere. Existing fragments: single-proposal spot prediction (A2's POLICY_PARKING_POSE, ranking explicitly TODO); path/goal conditioning (PolicyPathConditioner, goal late-fusion on Wonjoon's branch); LA conditioning of the diffusion OrdinaryHead (baa3912b39c0 on soham/affinity-guided-diffusion); unused AR machinery (AutoRegressiveActionHead, wayve/ai/zoo/autoregressive.py:13, no call sites).

Key data gap

In all pipelines an “anchor” is an event frame (gear-to-park, first-movement), not a spatial spot; PARKING_POSE is a single hindsight GT pose. No multi-candidate spot label set exists anywhere. (VLM spot-availability annotation exists on sohamphade/parking-annotation-pipeline.)

▸ Phase-1 addenda — sibling branches, the real WTA, the VLM pipeline, the design docs §3.5 · 2026-06-12

Soham's branches

soham/dynamic-horizon-path[-clean], soham/affinity-guided-diffusion[-clean] — clean PRs #114772/#114773 open, no reviews. Dynamic horizon is the most mature item: speed-bucketed path horizon 30/60/120/180/240 m with horizon-normalized diffusion targets, a PathHorizonSTAdaptor, deployment-side mirror, Welford scale versioning, and a trained 100k-step checkpoint (…dhla1 — which also trains latent-action conditioning of the OrdinaryHead: 2 s endpoint codebook added to cond tokens after path conditioning). Affinity guidance is training-free DDIM steering toward POLICY_AFFINITY_POINTS [B,M≤8,2]: v1 (gradients on noisy iterates) produced backwards/U-turn paths; v2 fixes it (gradient only on the predicted clean sample, L2-normalized, same displacement applied to the iterate; scale 0.1–0.3). Unit-tested incl. bit-identical no-op; never trained/evaluated; “Option B” (learned conditioning) never implemented. The bev_clicker base tool is merged; guided-diffusion wiring is branch-only.

Wonjoon's branch

wonjoongoo/diffusion-v4-parking-path-pred — the merged PR #106346 came from a separate clean re-implementation. Built and then dropped on merge: ParkingPoseSTAdaptor (Fourier (x,y,yaw) → 1 token; early fusion beat late fusion — late fusion turned off twice; yaw conditioning abandoned via yaw_dropout=1.0), data-side 50% goal dropout (the de-facto CFG), and analytic TorchScript-able endpoint loss-guidance (closed-form gradient through decode, √ᾱ-scaled, deployable --guidance_scale, default off). Goal-set/unset metric splits survived to main separately (#102692). The merged model has no goal input at all; the PR body confirms on-car single-proposal determinism is intentional pending ranking. Branches preserved under origin/aa/wonjoon_* — author off-project; revival = reproduction spike, not merge.

The real WTA

zmurez/pudo only, not main: AnnealedWTALoss — K=8 parallel ego/indicator/gear head banks + a mode classifier on a dedicated query token, annealed soft assignment softmax(−loss/τ) with τ: 10→1e-5 (converges to hard WTA; independently reproduces the 2024 aWTA paper), classifier trained to imitate the routing oracle (soft targets), per-context-frame routing, cross-frame consistency regularizers, EMA-smoothed mode logits at inference. Config mcv_new_phase2x_wta.yml. No quantitative results recorded anywhere; the parking-hub report itself flags “branch-tip evidence, not a launched-run proof”.

VLM annotation pipeline

sohamphade/parking-annotation-pipeline, PR #103667 open: 3-step CoT (Gemini 2.5 Flash) emitting per-frame multi-spot lists with type/availability/ego-size-fit/constraints (handicap yes, EV missing) — structurally the multi-candidate shape we need, but free-text fields, no spatial grounding (no box/BEV coords), single front camera, 3-sample prototype, local JSON. Built for CoT SFT text, not detector supervision.

Design docs (Google Drive)

The System Design Overview (Boris, 2026-04) sets the I/O contract — spot selection input (pixel/bbox), maneuver/destination preference enums, PSD output [N,4,3], 8 s trajectory-horizon target — and flags that long-term parking conditioning “requires adding state (memory) to the model” as an open item, with MPA sketched as an external visual path encoder + cached encodings keyed by position. The Multiple Driving Heads pre-read (Andrew English, May 2026) fixes the deployment paradigm: shared trunk (≈half the ST transformer) + per-mode heads (~25% capacity each; a 5-head setup fits Nissan AD2's 8 GB), one head/frame by deterministic rule, heads must be stateless — caching lives in the trunk; engine-swap alternatives rejected precisely because the temporal cache empties at switchover. Parking_SW_tech DRAFT_3 (Alon, Nov 2025): unified parking head with multi-channel output tensor (slot prob / occupancy / distance), USS as a small auxiliary branch; slot detection P>95% / R>90%, parking success >95% targets. Parking 2026 plan slides: scope/milestones as in the roadmap; “parking model alignment into baseline (multi-head approach)” is the MS5 exit.

Production constraints that frame everything (Notion, June 2026)

Multi-head shift (May-5 weekly): the company moved from one unified model to freezing ~half the network and finetuning mode-specific heads; “parking merged into driving baseline via multi-head architecture” with deterministic mode switching is the MS5 productization gate — novel solutions should live inside a parking head/branch. Roadmap (Parking 2026 v2.0): MS2 P2P basic + Valeo demo (Jun–Jul) → MS3 multi-leg + limited PSD head + rear camera in BC/RL (Jul) → MS4 P2P F2, parking cameras, HMI, multi-level nav F1 (Aug–Oct) → MS5 multi-spot APA E2E (Oct–Jan 27). New I/O explicitly planned: rear camera, fisheye SVC, parking-preference input adaptor, PSD I/Os, 4D occupancy, USS safety shell. MPA (memory parking) out of 2026 scope — reassess end-Q2, i.e. now. Latency: diffusion head deliberately small; recurring TorchScript scriptability constraints; temporal feature caches assume a fixed sliding window. Known MS2 failure modes: reverse/gear-shift stability, end-of-route logic, standstill-in-drive — these three drive P0.
