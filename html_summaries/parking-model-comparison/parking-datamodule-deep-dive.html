How the SI Parking Datamodule Works

Detailed read-through of wayve/ai/si/datamodules/parking.py on boris/05-21-updated-pudo-config, with the relevant wiring in otf.py, parking_config.py, and route-map code.

Short version. The parking datamodule is a sample-level augmentation and labelling pipeline. It reconstructs a cleaner parking gear timeline, detects parking / parked / unparking states around neutral gear segments, optionally modifies route-map context, and rewrites several model-facing labels before batching.

Branch-specific boundary. This Boris branch enables the SI parking dataloader through ParkingDataConfig defaults, but does not produce Wonjoon-style long-horizon POLICY_PATH by default because policy_path_num_points=0.

Mental Model

Think of parking processing as a temporary side pipeline inserted into the OTF datapipe. The incoming sample is still a normal (table, data) pair. parking.py wraps it as (table, scratch_table, data), fills scratch state with resolved indices and full-resolution time series, writes final model labels into data, then removes the scratch table.

Input sample (table, data)
  • vehicle, policy, path, and odometry data already inserted
  • table still has full frame-level time series
>
Scratch stage fill_parking_scratch_table
  • resolve origin and future lookahead indices
  • read speed, distance, timestamps, gear
  • construct clean parking gear series
>
State detection add_parking_state
  • detect parking, parked, unparking
  • write model-facing parking keys
  • store optional route shortening anchor
>
Target rewrites Augment and clean labels
  • unparking gear augmentation
  • strip leading standstill
  • clamp policy after neutral gear
>
Output sample (table, data)
  • scratch table dropped
  • downstream map/camera/provenance pipeline continues

parking.py

The central entrypoint is insert_parking_data(). It has two modes: delegate to the simpler zoo parking dataloader when use_zoo_dataloader=True, or run the SI-specific pipeline when False. This branch uses the SI path.

insert_parking_data -> _init_scratch -> fill_parking_scratch_table -> add_parking_state -> optional set_stopping_mode -> optional compute_policy_path -> augment_unparking_gear -> optional strip_leading_standstill -> clamp_policy_at_first_neutral -> optional augment_standstill_gear -> optional apply_parking_goal_dropout -> _drop_scratch

1. ParkingDataConfig

ParkingDataConfig groups all parking detection and augmentation knobs. The important separation is between detection thresholds, route-context training behavior, output augmentation, and policy-path generation.

Route contextpark_mode_blackout_probability, enable_route_shortening_for_parking, enable_end_of_route_blackout, stop_route_offset_mChooses between giving the model explicit parking mode plus route blackout or shortened route context.

2. Scratch Table Construction

fill_parking_scratch_table() is the data extraction and normalization stage. It resolves table indices, grabs optional future pose/curvature arrays, then builds the gear series used by the detector.

Inputs Resolved indices
  • origin index from a literal int or table key
  • vehicle indices for current/past vehicle state
  • policy indices for future policy targets
  • additional lookahead indices for parking detection
Signals Full-resolution arrays
  • timestamps in seconds
  • cumulative distance
  • speed in km/h
  • raw gear direction
  • optional indicator lights
Optional path support Future parking poses
  • uses odometry to compute relative future poses
  • stores additional parking pose in scratch
  • stores matching curvature if present
  • used by standstill stripping and optional policy path

3. Gear Reconstruction

The parking detector relies heavily on P/N segments, so the first hard problem is making gear trustworthy. The code can either use signed speed directly, or reconstruct gear from speed and validated P/N segments. Those modes are mutually exclusive.

StepCode behaviorReason
Speed-derived D/RSpeed above 0.5 km/h becomes forward; below -0.5 km/h becomes reverse; near-zero remains unknown.Moving direction is more reliable than noisy CAN gear for D/R.
Validated P/NOnly original neutral segments lasting at least min_duration_sec are kept.Short P/N blips should not create parking events.
MergeValidated P/N only replaces unknown speed-derived frames.Preserve strong motion evidence while recovering parked segments.
BackfillUnknowns are filled from the next valid gear.Creates a complete gear series for downstream indexing.
CleanupShort reverse or neutral segments can be replaced by adjacent gear.Removes parking-specific gear-label glitches.
Standstill expansionP/N segments are expanded backward/forward over adjacent stopped frames.Human drivers stop before and after shifting to P/N.

4. Parking State Detection

_compute_parking_state() treats clean neutral segments as anchors. It returns a ParkingStateResult containing boolean states plus timing, distance, and segment metadata.

Priority 0 Parked state
  • origin lies inside a neutral segment
  • goal distance is zero
  • segment start/end are stored for later augmentation
Priority 1 Parking state
  • find first future neutral segment
  • accept if within time threshold or distance threshold
  • goal distance is distance to neutral entry
Priority 2 Unparking state
  • find closest past neutral segment
  • scan forward after it for reverse gear and standstill
  • origin inside that exit interval becomes unparking

Known limitation. The current unparking detector only catches reverse-out unparking. The code comment says forward-unparking from P/N to D is missed, even though it may be safe to support because upstream neutral segments are already validated.

OTF Wiring

In otf.py, parking is inserted after the datapipe has already loaded frame/run data, odometry, vehicle data, policy data, and path data. It happens before intervention augmentation, camera loading, map insertion, route/indicator augmentation, and batching.

make_driving_datapipe -> load_frame_tables -> set_odometry_data -> load_run_tables -> insert_vehicle_data -> insert_policy_data -> optional load_paths + insert_path_data + filter_bad_paths -> insert_parking_data -> optional intervention / safety augmentation -> optional insert_parking_stop_route_position -> insert_map_data -> optional route blackout / navigation cleanup -> camera, radar, lidar, provenance, final transforms
Lookahead and past context Parking changes loaded window sizes
  • lookahead_sec can increase lazy future frame loading.
  • past_sec can increase additional past context in the timeslicer.
  • _make_clipped_lookahead_indices clips future indices near run boundaries instead of dropping the sample.
Validation behavior Route perturbations are train-only
  • For non-train datapipes, otf.py replaces parking config with route shortening disabled.
  • It also disables end-of-route blackout and navigation cleanup.
  • Parking labels can still be produced, but route-context stochasticity is removed.

Route Shortening and Route Maps

Route-shortening is the bridge between parking detection and the map input. parking.py writes stop-route index/fraction fields, then the route map datapipe consumes them before rendering MAP_ROUTE.

parking.py Store stop anchor
  • add_parking_state may store lookahead entry index.
  • insert_parking_stop_route_position turns it into route index/fraction.
  • Parking can jitter the stop anchor by stop_route_offset_m.
routes pipe Shorten route polyline
  • Parking uses _shorten_route_polyline_to_stop.
  • Unparking uses _shorten_route_polyline_from_stop.
  • Unparking route shortening is not jittered.
route renderer Render final map
  • generate_route_map_from_config receives the shortened polyline.
  • Map image generation itself is generic and parking-agnostic.
  • Parking-specific behavior is upstream in the route pipe.
